# Google Health MCP 0.3.0 cutover and rollback

This runbook owns the production boundary for the stable OAuth/JWT, Google DPoP,
consent, and typography release. It contains no secret values. The live task state
and operator/time gates remain in `.tasks/tasks/q2.md`.

## Preconditions

- The exact candidate commit passes the full Vitest suite, TypeScript, a clean
  production build, diff checks, and the official modern/stateless-legacy SDK clients.
- Migrations `0004_cuddly_bug`, `0005_gifted_tyger_tiger`, and
  `0006_lonely_earthquake` have passed one isolated Neon apply/verify/rollback rehearsal,
  including PostgreSQL failure injection and a forced reconnect-vs-refresh row-lock race.
  Old code has been proven to ignore the additive tables/columns.
- Data-only migration `0007_oauth_refresh_scope_compat` expands only active public v2
  registrations whose scopes are a subset of this server's six supported scopes. It does not
  alter consent, tokens, secrets, Google Health state, or legacy OAuth rows. Old and new code both
  accept the expanded registration rows.
- Vercel remains Node 24 + Fluid in `iad1`; no paid-plan prompt is present.
- The prior READY 0.2.1 deployment is recorded as the **pre-DPoP-reconsent** rollback artifact.
- Legacy OAuth client/token/consent tables remain intact.
- Google reconsent is forbidden until a separate DPoP-capable rollback artifact has been built
  and qualified. Source commit `9f99e9b` on `codex/dpop-rollback` is immutable. Production
  deployment `dpl_E8TFtPHHZ4SXh2FJLRcoTUGzfjqj` is READY with three Node functions in `iad1`;
  both configured Codex MCP connections passed authenticated `ping`, and a non-mutating sync
  status read passed. Preview `dpl_AYwLr9CUSc6vK9Z4E9evWs8XFJrH` remains build evidence only
  because preview intentionally lacks the production Better Auth secret. Reconsent and
  destructive cleanup require fresh owner approval immediately before the action.

## Production cutover

1. Capture aggregate-only counts for legacy registrations/tokens/consents, Google
   connections/tokens, and the absence of all six additive tables plus the four generation/
   thumbprint columns introduced by `0005`–`0006`.
2. Apply migrations `0004`–`0007` to the production main branch before deploying the new code.
3. Verify six additive tables, their constraints/indexes, all four new columns, zero new
   provider/DPoP rows, and unchanged legacy/Google counts.
4. Deploy recovery commit `9f99e9b` with the production environment, verify the legacy auth
   path plus an authenticated `ping`, and record the immutable Vercel deployment ID. **Complete:**
   `dpl_E8TFtPHHZ4SXh2FJLRcoTUGzfjqj` is the post-reconsent rollback target; do not promote the
   preview artifact.
5. Push the exact 0.3.0 commit to `main` and wait for the Vercel deployment to become
   READY in `iad1`. **Complete:** commit `0dda866`, deployment
   `dpl_5h11asJsx4hRJkrebvANHqRrkdTZ`.
6. Verify authorization/OpenID/protected-resource metadata, JWKS, unauthenticated MCP
   challenge, public DCR, malformed/wrong-resource rejection, and form-only token input.
   **Complete:** all anonymous gates passed; the exact synthetic registration was removed and
   v2 token/consent rows remain empty.
   For the 2026-07-31 desktop refresh-compatibility patch, additionally verify that protected
   resource metadata and the initial 401 omit optional scope narrowing, authorization-server
   metadata still advertises all six scopes including `offline_access`, and a true missing write
   scope still returns `scope="health:write"`.
   **Complete for the anonymous/live boundary:** deployment
   `dpl_BXX6gM9UXVP7yRsNHMKEdnGzVXAR` passed metadata, 401, S256, refresh-grant, and a controlled
   all-six-scope public DCR whose synthetic row was removed. Owner reauthentication remains the
   refresh-issuance oracle.
7. Pause for the owner before removing/revoking old connector state. Then reconnect each named
   MCP client and prove discovery, `ping`, and one non-mutating live Health read.
8. Pause for fresh owner approval. Run one explicit Google Health `prompt=consent` reconnect.
   The prior encrypted credential remains active unless the DPoP-bound refresh token and key
   commit atomically.
9. Prove one Google refresh and a subsequent non-mutating live read. From this point onward,
   raw 0.2.1 is no longer a valid rollback target.

Never paste a connection string into a shell command, task record, commit, log, or chat.

## Application rollback epochs

**Before Google DPoP reconsent:** restore the recorded 0.2.1 Vercel deployment. It uses only
the untouched legacy OAuth tables and ignores every additive 0.3.0 table/column.

**After Google DPoP reconsent:** never restore raw 0.2.1. The bound refresh token requires its
persisted DPoP private key and proof logic. Restore production deployment
`dpl_E8TFtPHHZ4SXh2FJLRcoTUGzfjqj` (commit `9f99e9b`) or forward-fix on 0.3.x. Retain
`google_health_dpop_key` and every generation column.

Do not drop additive state during an application incident; preserving it keeps recovery possible.

Rollback is successful only when the prior deployment is READY, legacy metadata/auth
works, an authenticated `ping` passes, and Vercel shows no new database/auth error burst.

## Schema rollback (rehearsal/emergency only)

Use this only **before Google DPoP reconsent**, when 0.3.0 is no longer serving and preserving
new-provider state is unnecessary. It requires fresh owner approval. Drop in foreign-key-safe
order:

1. `google_health_dpop_key`
2. `mcp_oauth_access_token_v2`
3. `mcp_oauth_consent_v2`
4. `mcp_oauth_refresh_token_v2`
5. `mcp_oauth_client_v2`
6. `mcp_oauth_rate_limit_v2`

Then remove `oauth_tokens.dpop_thumbprint`, `oauth_tokens.credential_version`, and
`oauth_connections.credential_version`. `google_health_dpop_key.credential_version` disappears
with its table.

Then verify all six are absent and aggregate legacy/Google counts match the pre-migration
receipt. Never export token columns.

If a DPoP-bound Google refresh token has ever committed, this schema rollback is prohibited:
dropping its key destroys the only unattended refresh path.

## Seven-day acceptance and cleanup

Monitor errors, authorization failures, protocol era, latency, and Neon query counts for
24 hours and seven days. Only after every intended connector passes and the rollback window
is accepted may the legacy OAuth rows/tables be securely deleted. Pause for fresh owner approval
immediately before that destructive cleanup. It is a separate evidenced action, never bundled
into initial deployment. Legacy protocol support remains
until every active connector produces zero legacy requests for 30 consecutive days.
